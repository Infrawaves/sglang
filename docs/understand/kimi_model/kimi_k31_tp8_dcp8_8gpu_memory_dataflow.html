1. 配置与合法性

采用 cookbook 中 B300 统一部署的 High-Concurrency (DCP8) 配置（docs/src/snippets/configs/moonshotai/kimi-k3.1-pro.jsx:599-623，状态 "in-progress"）。同一个实例既做 prefill 也做 decode：

SGLANG_DCP_PUSH_COMBINE_MAX_ROWS=1536 SGLANG_CUSTOM_ALL_REDUCE_V2_MAX_SIZE_KB=32768 \
sglang serve --model-path <Kimi-K3.1-Pro> --trust-remote-code \
  --tp-size 8 --dcp-size 8 --dcp-comm-backend fi_a2a --ep-size 2 \
  --mem-fraction-static 0.85 --max-running-requests 64 \
  --reasoning-parser kimi_k3 --tool-call-parser kimi_k3
能通过 K3.1 的 DCP 检查（arg_groups/model_overrides/kimi_k3.py:214-245 的 _kimi_k31_dcp_overrides）：
  • dcp_size 必须是 2 的幂，并且能整除 tp_size：8 满足。
  • 不能开 prefill CP（--enable-prefill-cp 或 attn_cp_size > 1）和 HiSparse。投机解码只能用 DSPARK 或 DFLASH。PD 分离时只能用 Mooncake。
  • 通用约束 tp % dcp == 0（parallel_state.py:2673）满足。
  • 用 fi_a2a 时，K3.1 默认开启 --dcp-replicate-q-proj（_dcp_replicate_q_proj_default）。

Maas 线上的 K3.1 Prefill 实例用的是同样的形态：TP8 · DCP8 · EP2，2 节点 × 4 张 GB300，--dcp-comm-backend fi_a2a。所以第 4 节的 prefill 流程也适用于 PD 分离时的 Prefill 实例。

和纯 TP8 相比，权重有什么不同： 只多了 MLA Q 侧在 DCP 组内的复制，以及 V 预投影的权重。DCP 本身不切分权重，它切的是 KV。专家权重占大头，布局和 TP8 一样。
可以参考的实测值： Maas 记录过 K3 的 TP8 / EP8 Prefill，权重显存实测 214.67 GB/卡（Maas/tools/kv_calculator/src/params.js，日志 "Load weight end ... mem usage=214.67 GB"）。K3.1 的 DCP8 · EP2 配置没有实测数据，量级应当相近。

cookbook 原话："DCP is the only axis that shards it"，即只有 DCP 会切分 MLA KV。所以 DCP8 让每张卡能放下的 token 数，大约是 TP8 的 8 倍。但 KDA 状态池仍然限制着并发请求数（"The KDA state pool is the concurrency ceiling"）。这就是这个配置叫 High-Concurrency 的原因：适合长上下文和多请求，KV 不再是瓶颈。

5. Prefill 阶段的数据传递

以一个 16384 token 的 chunk 为例。DCP 不切分 token 的计算：8 张卡都处理全部 16384 个 token，按普通 TP8 的方式切分权重。DCP 只影响 KV 存在哪张卡上、怎么读回来。

① 入口

8 张卡拿到同一批 token，做 embedding（词表并行，需要一次 all-reduce，推测）。

② DSA/MLA 层（24 层）

  1. 算出新 token 的 KV。 每张卡都对全部 16384 个 token 算出 latent KV（512+64 维）和 indexer K，8 张卡的结果相同。
  2. 只有 owner 写入。 写 cache 时，非 owner 的 slot 映射到空槽（translate_write），所以每张卡只存位置 p % 8 == rank 的那 1/8 新 token。不需要通信
  3. 把全部 KV 和 indexer K 拼回来。 all-gather（8 卡） 每张卡读出本地那 1/8 的 KV 和 indexer K。注意范围是前缀加本轮新 token，不只是新 token。然后按位置顺序 gather 回每个请求的完整序列（dcp_gather_request_rows，在 dsa_backend.py:1392 的 dcp_gather_kv_cache 和 dsa_indexer.py:1930- 的 _dcp_gather_index_k 里调用）。代码注释："so the ragged indexer runs unchanged"。
  4. indexer 选 top-k。 对完整的 indexer K 做 ragged 打分，选出 top-k。K3.1 的 indexer 在行数足够多时，会把 query 行拆到 attention-TP 各 rank 上分别计算，再汇总（_indexer_tp_split，dsa_indexer.py:464-466）。
  5. 稀疏 MLA。 每张卡用自己那 1/8 头，在 gather 来的完整 KV 上做稀疏 attention，结果是精确的。代码注释："K3.1's sharded DSA prefill attends over the gathered KV instead"（forward_mla.py:207-210）。prefill 阶段不做 LSE 合并。
  6. 输出投影。 o_proj 按头 TP8 切分，得到部分和，再 all-reduce（8 卡）。

第 3 步每层 gather 的是这批请求整个序列的 KV 和 indexer K，约 788 B × 序列长度。命中的前缀越长，这一步的开销越大。这是 DCP 在 prefill 阶段为了"KV 只存一份"付出的代价。临时 buffer 用完就释放，不常驻显存。

③ KDA 层（69 层）

和普通 TP8 完全一样：每张卡对全部 token，用自己的 12 个头，从本地的前缀状态出发做递归，并更新状态。o_proj 的部分和做 all-reduce。DCP 对 KDA 层没有任何影响。

④ MoE 层（92 层）

EP2 × TP4：每张卡用自己持有的 448 个专家的 1/4 切片，对全部 token 计算。latent 部分和与共享专家部分和在 TP8 内 all-reduce。K3 有 all-reduce 和 norm 融合的 kernel（k3_ar_fusion）。

⑤ 出口

最后一层之后计算 logits，采样出第一个 token。8 张卡持有相同的 hidden，不需要 gather 行。

6. Decode 阶段的数据传递

decode 是 DCP 主要发挥作用的阶段。每个请求每步只有 1 个新 token。历史 KV（不管当初是命中的前缀还是之前生成的）都按 p % 8 分散存储，每张卡只对自己那 1/8 计算。

DSA/MLA 层

  1. Q： 因为开了 --dcp-replicate-q-proj，每张卡在本地算出全部头的 Q，不需要 all-gather（is_dcp_q_replicate_phase，forward_mla.py:213-222）。
  2. 新 token 的 KV： 每张卡都算，只有 p % 8 号卡写入。
  3. indexer，先选本地候选： 每张卡只对本地 1/8 的 indexer K 打分，选出本地 top-k 作为候选（_local_candidates）。
  4. 合并成全局 top-k： all-gather 候选（分数加全局位置），再合并出精确的全局 top-k（dcp_global_topk）。8 或 16 卡、并且支持 multicast 时，用单个 kernel DcpTopKMerge 完成合并。合并结果是精确的：全局 top-k 里的每个 key，在它所在卡的本地 top-k 里也一定排得上（dsa_dcp_sharded.py 文件头注释）。
  5. 只保留本卡的 slot： dcp_localize_compact 从全局 top-k 中挑出属于本卡的 slot。
  6. 本地稀疏 attention： 用 FlashMLA 对全部头，在本卡选中的 KV 上计算，得到部分输出（latent 空间）和 LSE。
  7. V 预投影（dcp_v_preproject）： 每个头的 V 投影是线性的，可以和 LSE 加权合并交换顺序。所以先把部分输出从 512 维投影到更窄的 v_head_dim，再交换，减少通信量（forward_mla.py:1041-1066）。
  8. LSE 合并： push-combine / fi_a2a（8 卡） 把各卡的部分结果按头交换，并按 LSE 合并。每张卡最后拿到自己那 1/8 头的完整输出（dcp_push_combine_reduce 或 dcp_a2a_lse_reduce）。SGLANG_DCP_PUSH_COMBINE_MAX_ROWS=1536 控制单 kernel push-combine 的行数上限。
  9. 输出投影： o_proj 按头 TP8 切分，再 all-reduce。

KDA 层

每张卡对 12 个头做一步递归，原地更新状态，o_proj 部分和做 all-reduce。

MoE 层

EP2 × TP4 计算，all-reduce。

7. PD 分离时的 KV 传输

本例是统一部署，没有 PD 传输。如果拆成 Prefill（TP8 · DCP8）和 Decode（例如 cookbook 的 B300 Decode Balanced：TP8 · DCP8 · EP2，或 Maas 线上的 TP32 · DP4 · DCP8）：

数据传输方式
MLA KV + indexer K两边 DCP 相同，Mooncake 按页传输：rank r 发给 rank r。注释原文："Mooncake moves a DCP-1 prefill's KV row by row and a same-DCP prefill's page by page, and raises on any other DCP pair"（model_overrides/kimi_k3.py）。也就是说，DCP 不同的组合只支持 DCP1 → DCPn
KDA 状态两边都按头切 8 份时，rank r 发给 rank r。Maas 的 Decode 有 attention DP4，每个 DP 组内部是 TP8 · DCP8，对应关系一样

9.1 Prefill 阶段每个子层的计算拆分

上表"每卡处理的 token 行"指的是激活值的行数，不是计算量。下面按子层拆开，以一个 16384 token 的 chunk 为例。"全部 token × 1/8 头" 表示每张卡处理全部 token，但只算自己那 1/8 的头或权重切片。

子层TP8TP8 + PCP8TP8 + DCP8
norm、Attention-Residual 聚合全部 token（复制计算）1/8 token全部 token（复制计算）
MLA：latent KV 投影、indexer K全部 token（复制计算，latent 只有一个头）1/8 token，算完 gather全部 token（复制计算）
MLA：Q 投影、稀疏 attention、o_proj全部 token × 1/8 头1/8 token × 全部头全部 token × 1/8 头
KDA（投影、短卷积、递归、o_proj）全部 token × 1/8 头全部 token × 1/8 头（先 gather 完整序列）全部 token × 1/8 头
MoE：router、latent down 投影全部 token（复制计算）全部 token（gather 后，复制计算）全部 token（复制计算）
MoE：专家全部 token × 自己的切片全部 token × 自己的切片全部 token × 自己的切片（EP2 × TP4）
MoE：latent up 投影全部 token（复制计算）1/8 token（reduce-scatter 之后）全部 token（复制计算）

依据：PCP 下 KDA 先 gather 完整序列，再按头切分（kimi_k3.py:2667-2722）；PCP 下 MoE 走 _forward_cp_shard_rows，先 "fused front over every gathered row"，reduce-scatter 之后再在本卡的行上做 up 投影（kimi_k3.py:1977-2005）；DCP prefill 下 MLA 每张卡用自己那 1/8 头（forward_mla.py:207-210），其余部分和 TP8 相同。

怎么理解：
  1. KDA 在三种配置下的计算完全一样，都是全部 token × 1/8 头。PCP8 并没有减少 KDA 的计算，只是多了一次 gather 和一次 reduce-scatter。DCP 对 KDA 没有任何影响。
  2. MLA 的核心计算量在 TP8 和 PCP8 下也基本一样。 "全部 token × 1/8 头" 和 "1/8 token × 全部头"，每张卡的 FLOPs 相同。
  3. PCP8 真正省掉的，是 TP8 下复制计算的那些部分：latent KV 投影、indexer K、norm、Attention-Residual 聚合，以及 MoE 的 up 投影。在 TP8 下，8 张卡都对全部 token 重复做这些计算；在 PCP8 下，每张卡只做 1/8。MoE 的 router 和 down 投影在 PCP8 下仍然复制计算。
  4. DCP8 在 prefill 阶段的计算和 TP8 一样，区别只在 KV 存在哪里、怎么读回来。
