1. 配置说明与合法性

题目里的"PCP 并行数 8 + TP 并行数 8"，理解为 --tp-size 8 --enable-prefill-cp --attn-cp-size 8，8 张卡同时构成 TP 组和 CP 组。

这套配置能通过 K3.1 的参数检查。 K3.1 的 prefill CP 只能走 CP-TP group sharing 路径（arg_groups/cp_tp_group_sharing_hook.py）。这条路径要求：

  • attn_cp_size == tp_size：8 == 8，满足。
  • --cp-strategy interleave：必须显式指定。
  • KDA 头数能被 8 整除：cookbook 有 TP8 的配置，说明满足。
  • 不能开 --dcp-size > 1、--enable-mixed-chunk、--moe-dp-size > 1、attention DP；不能作为 --disaggregation-mode decode；投机解码只能用 DFLASH。
这套配置没有经过验证。 cookbook 给 B300 Prefill 的只有 Low-Latency（纯 TP8，不开 PCP，kimi-k3.1-pro.jsx:624-650）和 High-Throughput（PP4 × PCP2）两套。下文以 cookbook 的 TP8 Prefill 配置为基础，再加上 PCP8 相关的参数。MoE 用默认的 TP 切分（不设 --ep-size，SM100 上默认的 runner 是 flashinfer_mxfp4）。换成 MegaMoE EP8 时的差异见第 10 节。 
sglang serve --model-path <Kimi-K3.1-Pro> --trust-remote-code \
  --tp-size 8 --enable-prefill-cp --attn-cp-size 8 --cp-strategy interleave \
  --mem-fraction-static 0.88 \
  --chunked-prefill-size 16384 --max-prefill-tokens 16384 \
  --reasoning-parser kimi_k3 --tool-call-parser kimi_k3 \
  --disaggregation-mode prefill --disaggregation-transfer-backend mooncake \
  --disaggregation-bootstrap-port 8998

3. 8 卡 rank 拓扑

  • TP 组是 [0..7]，CP 组直接复用 TP 组（parallel_state.py:2753：_ATTN_CP = _TP）。
  • attn_tp_size = 8 / 1 / 8 = 1（runtime_context.py:73），所以 MLA/DSA attention 在 8 张卡上都是完整复制的。
  • KDA 的头按 TP8 切分。CP-TP sharing 下 linear_attn_parallel_group() 返回 "tp"（runtime_context.py:477）。
  • MoE 不设 EP 时，路由专家、共享专家和 dense FFN 都按 TP8 切分。latent 的 down / up 投影和 router 是复制的（kimi_k3.py:816-834 用的是 ReplicatedLinear）。
  • interleave 策略：token 序号 i 分给 rank i % 8（layers/cp/interleave.py）。

5. 显存分布：KV cache 与 KDA 状态

缓存8 张卡上的分布每张卡的成本（估算）Prefill 时怎么写入Decode 时怎么写入（统一部署）
MLA latent KV（FP8）+ indexer K，24 层复制 8 份：每张卡都存全部 token、全部 24 层约 18.9 KB/token/卡。128K 上下文的单个请求约 2.4 GB/卡每张卡只算 1/8 的新 token，8 卡 all-gather 后，每张卡写完整的一份（interleave.py 的 materialize_full_mla_kv / materialize_full_indexer_k_cache）8 张卡都算、都写同一个新 token
KDA 递归状态（FP32），69 层按头切 8 份约 52 MB × 每个请求的状态槽数（例如 extra_buffer 是 5 个）每张卡用完整序列，更新自己那 1/8 头的状态每张卡原地更新自己那 1/8 头

cookbook 原话："TP and PCP replicate the MLA KV; DCP is the only axis that shards it."，即 TP 和 PCP 都会复制 MLA KV，只有 DCP 会切分它。所以 PCP8 的 KV 显存和纯 TP8 完全一样，能容纳的 token 数不会增加。KV 池和 KDA 状态池之间的比例由 --mamba-full-memory-ratio 决定。

6. Prefill 阶段的数据传递

以一个 16384 token 的 chunk 为例。每张卡分到 2048 个 token（序号 i % 8 == rank）。命中缓存的前缀不参与切分，也不需要计算：它的 MLA KV 在每张卡上都有完整的一份，KDA 前缀状态在每张卡上有自己那部分头。

① 入口

  • prepare_cp_inputs 对全部 16384 个 token 做 embedding（kimi_k3.py:3801）。runner 按 interleave 规则取出本卡的 2048 行（eager_runner.py 的 _execute_extend_cp）。切分本身不需要通信
  • 之后的残差流，每张卡只保存本卡的 2048 行。

② DSA/MLA 层（24 层）

  1. 本卡对自己的 2048 行计算 Q、latent KV（512 + 64 维）和 indexer K。权重是复制的，所以每张卡都算全部头。
  2. all-gather（8 卡） 把 8 张卡上新 token 的 latent 和 indexer K 拼起来，恢复原始顺序，每张卡都写进 KV cache。
  3. indexer：本卡 2048 个 query 对"前缀 + 全部 16384 个新 token"的 indexer K 打分，选出 top-k。前缀是本地数据，不需要通信。
  4. 稀疏 MLA attention：本卡的 query 对选中的 KV 做计算，结果是精确的，不需要 LSE 合并。
  5. o_proj 也是复制的，输出就是本卡 2048 行的完整结果。不需要归约

③ KDA 层（69 层）

  1. all-gather（8 卡） KDA 按时间递归，需要完整的序列。先 gather 8 张卡的行，再 cp_interleave_to_sequence_order 恢复 token 顺序（kimi_k3.py:2667-2670）。
  2. 每张卡对全部 16384 个 token，用自己那 1/8 头，从缓存里的前缀状态出发计算递归，并把更新后的状态写回状态池。
  3. cp_sequence_to_interleave_order 把结果换回 interleave 的行顺序（kimi_k3.py:2719-2722），再过行并行的 o_proj，得到部分和。
  4. reduce-scatter（8 卡） 把 8 个部分和加起来，并只保留本卡的 2048 行（layer_boundary/ops.py 的 attn_cp_interleave_reduce_scatter）。

④ MoE 层（92 层，latent MoE，TP8）

CP-TP sharing 下，latent MoE 声明 output_on_cp_shards，走 KimiK3MoE._forward_cp_shard_rows（kimi_k3.py:1977-2005）：

  1. all-gather（8 卡） FFN 的输入在 CP 组内按 rank 顺序 gather（_cp_gathers_over_attn_cp，layer_boundary/layout.py:199），每张卡拿到全部 16384 行。
  2. fused front：对全部行计算 router（复制）、latent 的 down 投影（复制）和共享专家的 gate_up（TP8 切片）。
  3. 路由专家：每张卡对全部行，用自己那 1/8 的 intermediate 切片计算，得到 latent 的部分和。共享专家也得到部分和。
  4. reduce-scatter（8 卡）× 2 把 latent 部分和、共享专家部分和分别加起来，并分回本卡的 2048 行。
  5. 本卡在自己的行上做 latent norm 和 up 投影（复制的权重），再加上共享专家的输出。

KDA 的输出会 reduce-scatter，紧接着 MoE 的输入又要 all-gather，所以层边界可能把这两步合并成一次 all-reduce，或者做其他融合。实际执行以 layer_boundary 的计划为准，这里写的是逻辑上的数据流。

⑤ 出口

  • all-gather（8 卡） cp_gather_after_forward 把最后一层的 hidden 拼回完整序列（eager_runner.py:403），然后计算 logits，采样出第一个 token。

7. Decode 阶段

K3.1 的 CP-TP sharing 不允许 --disaggregation-mode decode（"Prefill only: the decode node serves TP (+ DCP)"）。所以这套布局要么作为 PD 的 Prefill 实例，此时 decode 在另一个实例上（见第 8 节）；要么统一部署，同一个实例自己做 decode。统一部署时的 decode 行为（按代码推断）：

方面行为
CP 是否生效不生效。is_cp_active 只在 EXTEND/MIXED 模式下成立（forward_mode.py:55），这时就是普通的 TP8。
激活值8 张卡处理同一个 decode 批次的全部 token。
DSA/MLA 层权重和 KV 都是复制的，8 张卡做同样的 attention 计算（8 倍冗余）。新 token 的 KV 8 张卡都写。不需要通信。--enable-cp-decode-attn-tp 可以消除这部分冗余，但它只支持 DeepSeek-V4 和 GLM-5.x，K3.1 不能用。
KDA 层每张卡更新自己 1/8 头的状态，o_proj 部分和做 all-reduce（8 卡）。
MoE 层专家 TP8，latent 和共享专家的部分和做 all-reduce（8 卡）。
显存和 prefill 一样：MLA KV 复制 8 份，KDA 状态按头切 8 份。

和纯 TP8 Prefill 的对比： 纯 TP8 的 KDA 和 MoE 本来就要在 8 卡内做归约，attention 则按头切分（MLA 只有 1 个 KV 头，KV 仍然是复制的）。PCP8 的主要变化有两个：一是 attention 部分按 token 分摊，每张卡只算 1/8 的 query，但要算全部头；二是每个 DSA 层多了一次 KV all-gather，KDA 和 MoE 层多了 gather / scatter 的行重排。权重和 KV 的显存占用都没有变化。

10. 换成 MegaMoE EP8 时的差异

如果加上 --moe-a2a-backend megamoe，按 cookbook 的说法，EP 会被设成 TP 的大小，也就是 EP8：

  • 路由专家：每张卡持有 896 / 8 = 112 个完整的专家，不再是所有专家的 1/8 切片。
  • 共享专家：不设 --shared-experts-tp-size 时会复制到每张卡（kimi_k3.py:719-735，注释写的是约 264 MB/层/rank，BF16）。
  • 数据流：MoE 直接在本卡的 2048 行上运行（layer_boundary/factories.py:162-174），通过 all-to-all 做 dispatch 和 combine，不再需要 gather 和 reduce-scatter。padding 行用 moe_num_token_non_padded 屏蔽。
  • token 上限：每卡的 token 数要满足 SGLANG_OPT_DEEPGEMM_MEGA_MOE_NUM_MAX_TOKENS_PER_RANK × ep_size 的上限（mega_moe_hook.py:239-245）。
