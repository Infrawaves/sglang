1. 先说明：为什么不是 "TP8 + PCP2（attention TP4）"

在 sglang 里，"PCP2 + TP4" 跑在 8 张卡上，字面写法是 --tp-size 8 --enable-prefill-cp --attn-cp-size 2。这时 attn_tp_size = tp / dp / cp = 8 / 1 / 2 = 4（runtime_context.py:73）。

Kimi-K3.1 不支持这种组合。 K3.1 的 prefill CP 只能走 "CP-TP group sharing" 这条路径（arg_groups/cp_tp_group_sharing_hook.py，K3.1 在 _SUPPORTED_MODELS 里）。这条路径要求 CP 组就是整个 TP 组：

if view.attn_cp_size != cfg.tp_size:
    raise ValueError("CP-TP group sharing requires --attn-cp-size == --tp-size, ...")

它还要求 --cp-strategy interleave，并且不能同时开启 --dcp-size > 1、--enable-mixed-chunk 或 --moe-dp-size > 1。另外，Kimi-K3（非 .1）完全不支持 --enable-prefill-cp（model_overrides/kimi_k3.py:54）。

所以下文用的是 cookbook 给出的 K3.1 单机 8 卡 PCP2 配置：TP2 · PCP2 · PP4。 每个 PP stage 用 2 张卡，这 2 张卡同时构成 TP 组和 CP 组；4 个 stage 一共 8 张卡。对应 cookbook 中 B300 Prefill 的 High-Throughput (PP4 × PCP2) 配置（docs/src/snippets/configs/moonshotai/kimi-k3.1-pro.jsx:652-689），状态是 "in-progress"，还没有标为 Verified。

cookbook 原话："TP and PCP replicate the MLA KV; DCP is the only axis that shards it."，即 TP 和 PCP 都会复制 MLA KV，只有 DCP 会切分它。

3. 采用的配置与 8 卡 rank 拓扑

SGLANG_PP_LAYER_PARTITION=24,24,24,21  CUDA_MODULE_LOADING=EAGER \
sglang serve --model-path <Kimi-K3.1-Pro> --trust-remote-code \
  --tp-size 2 --pp-size 4 \
  --attn-cp-size 2 --enable-prefill-cp --cp-strategy interleave \
  --ep-size 2 --moe-a2a-backend megamoe \
  --mem-fraction-static 0.84 \
  --chunked-prefill-size 16384 --max-prefill-tokens 16384 \
  --pp-min-chunked-prefill-size 4096 --pp-chunk-overhead-tokens 2000 \
  --cuda-graph-backend-prefill breakable --cuda-graph-max-bs-prefill 8192 \
  --schedule-policy fcfs --mamba-full-memory-ratio 0.62 \
  --reasoning-parser kimi_k3 --tool-call-parser kimi_k3 \
  --disaggregation-mode prefill --disaggregation-transfer-backend mooncake

rank 是怎么排的

  • world_size = tp × pp = 2 × 4 = 8。tp_rank = rank % 2，pp_rank = rank // 2（runtime_context.py 的 derive_spawn_ranks）。所以 GPU 2s 和 2s+1 组成第 s 个 stage。
  • attn_cp_size == tp_size，所以 CP 组直接复用 TP 组（parallel_state.py:2753：_ATTN_CP = _TP）。attn_tp_size = 1。
  • KDA 的头在 TP 组内切分（CP-TP sharing 下 linear_attn_parallel_group() == "tp"，runtime_context.py:477）。
  • MoE 是 EP2，每个 stage 内的 2 张卡各持有一半专家。
  • PP 层划分是 24 / 24 / 24 / 21 层。

GPU1tp/cp/ep rank 1

每个 stage 的 2 张卡同时是 TP 组、CP 组和 EP 组。同一 tp_rank 在相邻 stage 之间做 PP 的点对点传输（GPU0→2→4→6，GPU1→3→5→7）。

4. 显存分布：权重

每张卡只持有自己所在 stage 的那些层。在一个 stage 内部，2 张卡的分工如下：

权重在 stage 内两张卡上的分布依据
DSA/MLA attention（q/kv 投影、kv_b、o_proj、indexer）复制：两张卡各存一份完整的CP-TP sharing 下 attn_tp_size = 1；common/conn.py:440-442 注释："CP rank r holds every KV head"
KDA（q/k/v/β/gate 投影、o_proj）按头切分：每张卡存一半的头linear_attn_parallel_group()=="tp"；_stage_facts 注释："KDA heads span the TP group ... its output sums over TP"
MoE 路由专家（896 个）EP2：每张卡存 448 个--ep-size 2 --moe-a2a-backend megamoe
共享专家、router、latent 投影在 MoE 模块内部切分，本配置没有设置 --shared-experts-tp-size具体切分方式未逐一核实
dense FFN（1 层）、layernormdense FFN 按 _dense_mlp_parallel_group() 选择的组切分；norm 复制models/kimi_k3.py:393
embedding、lm_head（160K 词表）只在 stage 0 / stage 3 上prepare_cp_inputs："embed every token on the first pipeline rank"
粗略估算（以启动日志里的 weight memory 为准）： 2.8T × 约 0.53 B/参数 ≈ 1.49 TB。权重主要是专家，按 PP4 × EP2 均分，每张卡约 1.49 TB / 8 ≈ 185 GB 左右。再加上 stage 内复制的 MLA attention 权重，会多出一些。B300 每卡 288 GB，--mem-fraction-static 0.84 给的静态预算约 242 GB，扣掉权重后剩下几十 GB 给 KV 池和 KDA 状态池。两个池之间的比例由 --mamba-full-memory-ratio 0.62 决定。

5. 显存分布：KV cache 与 KDA 状态

K3.1 有两类缓存，分别对应两种 attention 层：

缓存大小与什么成正比在 stage 内两张卡上的分布Prefill 阶段Decode 阶段（统一部署时）
DSA/MLA latent KV（FP8）+ indexer Ktoken 数 × 本 stage 的 DSA 层数复制：两张卡都存这个请求的全部 token新 token 在本卡算出一半后，all-gather 补齐，两张卡都写完整的一份（interleave.py 的 materialize_full_mla_kv / materialize_full_indexer_k_cache）新 token 两张卡都写
KDA 递归状态（FP32）请求数 × 槽位数，和长度无关按头切分：每张卡存一半头的状态每张卡用完整序列更新自己那一半头的状态每张卡原地更新自己那一半头
DFLASH 草稿 KV（如果启用）token 数草稿用普通 TP 运行（cp_tp_group_sharing_hook.py 注释）本配置没有开启投机解码

MLA KV：全部 token × 本 stage DSA 层
KDA 状态：头 0..H/2
GPU 2s+1 权重：MLA 全部 + KDA 头 H/2..H + 专家 448..895

KDA 状态：头 H/2..H
按 cookbook 的数字估算每张卡的缓存成本：
  • MLA + indexer KV：全模型 18.9 KB/token。PP4 下每个 stage 约 1/4，也就是约 4.7 KB/token。CP 复制不节省，所以两张卡各约 4.7 KB/token。128K 上下文的单个请求约 0.6 GB/卡。
  • KDA 状态：全模型约 416 MB/请求。PP4 分到每个 stage 约 1/4，TP2 再减半，每张卡约 52 MB 乘以每个请求的状态槽数（例如 extra_buffer 策略是 5 个，见 Kimi-K3.mdx 的计算器说明）。
  • 每个 stage 实际有几个 DSA 层，以模型 config 的 full_attn_layers 为准。上面按 69:24 的比例粗略估算。

6. Prefill 阶段的数据传递

以一个 16384 token 的 chunk 为例（--chunked-prefill-size 16384）。interleave 策略把整批 token 按序号的奇偶分给 2 个 CP rank，每个 rank 8192 个（interleave.py:227-242）。命中缓存的前缀不参与切分，也不需要计算，它的 KV 和 KDA 状态已经在缓存里。

① 入口（只在 stage 0）

  • 两张卡上的 scheduler 拿到同一批请求。prepare_cp_inputs 在第一个 PP rank 上对全部 token 做 embedding（kimi_k3.py:3801）。
  • runner 按 interleave 规则取出本卡的行：GPU0 取偶数号 token，GPU1 取奇数号（eager_runner.py 的 _execute_extend_cp → cp_shard_model_inputs）。不需要通信
  • 之后的所有层，残差流都只保存本卡的 8192 行。

② DSA/MLA 层（每个 stage 约 6 层）

  1. 本卡对自己的 8192 行计算 Q、latent KV（512 + 64 维）和 indexer K。权重是复制的，所以不需要切头。
  2. all-gather（CP 组，2 卡） 把两张卡上新 token 的 latent 和 indexer K 拼起来，恢复原始顺序，两张卡都写进 KV cache（materialize_full_mla_kv、materialize_full_indexer_k_cache）。
  3. indexer：本卡的 Q 对 "前缀 + 全部新 token" 的 indexer K 打分，选出 top-k。前缀 KV 本来就在本地，不需要通信。
  4. 稀疏 MLA attention：本卡的 Q 只对选中的 KV 计算，结果是精确的，不需要 LSE 合并。
  5. o_proj 也是复制的，输出就是本卡 8192 行的完整结果。不需要归约

③ KDA 层（每个 stage 约 18 层）

  1. all-gather（TP=CP 组） KDA 是按时间递归的，需要完整的序列。在层边界把两张卡的行按 rank 顺序拼起来，然后 cp_interleave_to_sequence_order 把它们恢复成原始 token 顺序（kimi_k3.py:2667-2670）。
  2. 每张卡对全部 16384 个 token，用自己那一半头的权重，从缓存里的前缀 KDA 状态出发计算递归，并把这一半头的状态写回状态池。
  3. cp_sequence_to_interleave_order 把结果换回 interleave 的行顺序（kimi_k3.py:2719-2722）。o_proj 是行并行的，每张卡得到的是部分和。
  4. reduce-scatter / all-reduce（TP 组） 把 TP 的部分和加起来，同时只保留本卡的 CP 行（layer_boundary/ops.py 的 attn_cp_interleave_reduce_scatter / cp_take_back_in_token_order）。

④ MoE 层（MegaMoE，EP2）

  1. 使用 a2a 后端时，FFN 直接在本卡的 attention 行上运行（layer_boundary/factories.py:162-174），interleave 的 padding 行用 moe_num_token_non_padded 屏蔽（interleave.py:167）。
  2. all-to-all dispatch（EP 组，2 卡） 每个 token 按 top-16 路由，发给持有对应专家的卡。
  3. 本卡计算自己的 448 个专家，加上共享专家。
  4. all-to-all combine 把结果送回 token 所在的卡，得到本卡 8192 行的 MoE 输出。

非 a2a 的 latent MoE 走另一条路径：先在 CP 组内 gather 全部行，算完后用 reduce-scatter 把 latent 和共享专家的部分和分回本卡的 CP 行（KimiK3MoE._forward_cp_shard_rows，kimi_k3.py:1977）。本配置用的是 MegaMoE，所以走 a2a 路径。

⑤ stage 之间（PP）

  • P2P send/recv stage s 的 rank r 把本卡 8192 行的 hidden states（以及 K3 的 attention-residual 相关张量）发给 stage s+1 的 rank r。注释原文："a later pipeline rank receives its CP shard through the PP proxy"。
  • PP 会让多个 chunk 交错执行：stage s 处理 chunk c 时，stage s+1 在处理 chunk c-1（--pp-min-chunked-prefill-size、--pp-chunk-overhead-tokens）。

⑥ 出口（只在 stage 3）

  • all-gather（CP 组） cp_gather_after_forward 把两张卡的行拼回完整的序列（eager_runner.py:403），再计算 logits 并采样出第一个 token。
  • PD 模式下，第一个 token 和 KV 一起交给 Decode 实例（见第 8 节）。

7. Decode 阶段

cookbook 里这套 PP4 × PCP2 配置只用作 PD 分离的 Prefill 角色，decode 在另一个实例上运行。为了回答"同一套布局在 decode 阶段是什么样"，下面按代码推断统一部署（不做 PD 分离）时的行为：

方面行为
CP 是否生效不生效。is_cp_active 要求 EXTEND/MIXED 模式（forward_mode.py:55），decode 不满足。
激活值stage 内两张卡处理同一个 decode 批次的全部 token，不切分。
DSA/MLA 层权重和 KV 都是复制的，两张卡做同样的 attention 计算（冗余）。新 token 的 latent KV 两张卡都写，不需要通信。用来消除这部分冗余的 --enable-cp-decode-attn-tp 只支持 DeepSeek-V4 和 GLM-5.x（cp_decode_attn_tp.py 的白名单），K3.1 不能用。
KDA 层每张卡更新自己那一半头的状态。o_proj 部分和在 TP 组内 all-reduce。
MoE 层EP2 all-to-all dispatch/combine。
PP每一步 decode 都要依次经过 4 个 stage，每个 stage 之间做一次 P2P。
显存和 prefill 一样：MLA KV 在 stage 内复制，KDA 状态按头切分。decode 阶段 PCP 不减少 KV 显存。

这说明了为什么 PCP 适合 Prefill 实例：它只在 prefill 阶段降低 TTFT，decode 阶段既有冗余计算，也没有节省 KV。

8. PD 分离：Prefill 到 Decode 的 KV 传输

cookbook 中与之配对的 B300 Decode 实例（Balanced 配置）是 --tp-size 8 --dcp-size 8 --dcp-comm-backend fi_a2a --ep-size 2（kimi-k3.1-pro.jsx:690-）。

数据Prefill 侧（TP2 · PCP2 · PP4）Decode 侧（TP8 · DCP8 · EP2）传输方式
MLA latent KV + indexer K每个 stage 的 2 张卡各有一份完整的，覆盖本 stage 的 DSA 层按 token 分散到 8 张卡（pos % 8），每张卡持有全部 24 个 DSA 层Mooncake RDMA 注释写明：DCP1 的 prefill 发给 DCP8 的 decode 时按行发送，每一行发到 owner 卡（model_overrides/kimi_k3.py："Mooncake moves a DCP-1 prefill's KV row by row"）

每个 PP stage 只发送自己那部分层。Decode 侧会收齐 4 个 stage 的数据，才算这个请求的 KV 传输完成（Mooncake 连接里有对应的 pp_size > 1 处理，mooncake/conn.py:845）。

Decode 实例每一步的数据流：DSA 的 indexer 先在各卡本地选 top-k，再合并成全局 top-k（dsa/dsa_dcp_sharded.py）。各卡对本地的 KV 算出部分 attention 结果，通过 fi_a2a 按 LSE 合并。KDA 在 TP8 内 all-reduce，MoE 走 EP2。
