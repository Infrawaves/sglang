# GPU 前缀命中 A/B 测试

在 Prefill 机器、仓库根目录、已有 SGLang 运行环境中执行。需要 `requests`、`transformers`，以及本机模型 tokenizer。这里只测试 GPU 前缀命中的低并发性能；不是模型准确率测试。测量期间不要向同一服务发送其他请求，脚本会清空 Router 所管理的缓存。

## 1. 启动服务

A/B 使用相同代码、模型、拓扑、GPU、chunk size、HiCache 配置和日志级别，只改变窗口化开关。每轮切换后重启 Prefill 和 Decode；脚本不会自动终止或重启服务。

两端启动前设置（B 改为 `1`）：

```bash
export SGLANG_MOONCAKE_DCP_WINDOW_PACK=1  # A=0，B=1
export SGLANG_MOONCAKE_DCP_PACK_BUFFER_MB=128
export SGLANG_MOONCAKE_DCP_NVTX=0
export SGLANG_MOONCAKE_DCP_LOG_DETAILS=0
export SGLANG_DISAGG_PREFILL_EARLY_SEND_CACHED_PREFIX=1
```

单块默认 128 MiB，每个 Prefill PP rank 两块。GPU OOM 时整对按 `128 → 64 → 32 MiB` 降档；32 MiB 仍失败则报错。容量变量本身不会开启窗口化。正式性能比较不要开启 nsys。

Prefill 节点：

```bash
export PREFILL_HOST=10.51.1.3
export PREFILL_PORT=8000
export PREFILL_BOOTSTRAP_PORT=8998
bash test_scripts/prefill.sh
```

Decode 节点：

```bash
export DECODE_HOST=10.51.1.5
export DECODE_PORT=8001
export DECODE_BOOTSTRAP_PORT=8998
bash test_scripts/decode.sh
```

Prefill 机器另开终端启动 Router：

```bash
export PREFILL_IP=10.51.1.3
export PREFILL_PORT=8000
export PREFILL_BOOTSTRAP_PORT=8998
export DECODE_IP=10.51.1.5
export DECODE_PORT=8001
export ROUTER_HOST=10.51.1.3
export ROUTER_PORT=8848
bash test_scripts/router.sh
```

服务地址按实际部署修改。监听地址可以是 `0.0.0.0`，客户端和 Router 使用实际可达 IP。

Prefill/Decode 日志按实际窗口化配置自动标记 A/B，每次启动创建独立文件，例如：

```text
log/prefill-A-20260917-143000.xxxxxx.log
log/prefill-B-20260917-150000.xxxxxx.log
log/decode-B-20260917-150005.xxxxxx.log
```

时间戳加随机后缀避免同组重跑覆盖。`prefill-A-latest.log`、`prefill-B-latest.log`（Decode 同理）是各组最新启动日志的软链接，旧日志保留。链接更新代表启动尝试，不代表服务已就绪。若设置了 `MODE`，启动脚本会检查它与窗口化配置一致。

`bench.sh` 默认读取对应组的 `prefill-${MODE}-latest.log`；运行开始时解析成固定文件路径，并写入结果的 `prefill_log` 字段。可用 `LOG_DIR` 修改启动与 bench 的日志目录，或在 bench 中用 `PREFILL_LOG` 指定具体文件。每次仍须确认正在测试的服务与该日志对应。

## 2. 运行 A/B

A 服务就绪后，在 Prefill 机器运行：

```bash
export BASE=http://10.51.1.3:8848
export RESULT_DIR=ab-results/gpu-prefix-run1
MODE=A bash test_scripts/bench.sh
```

然后两端切换窗口化为 `1`，重启服务并等待 Router 可用，在相同结果目录运行：

```bash
MODE=B bash test_scripts/bench.sh
```

`MODE` 只是声明期望测试哪种路径，不会修改服务配置。客户端会检查本机 Prefill 日志：A 应有旧 pack 容量不足回退；B 应有窗口分配、Gather、成功发送和完成记录，且没有回退。缺失日志也会判为无效，不等于推理一定失败。

默认工作负载：

- 512K（524288）共享前缀 token + 16K（16384）新后缀 token；直接发送 token IDs，避免文本重新分词改变长度。
- 并发 1、输出 8 token、temperature=0、ignore_eos=true。
- 清缓存一次；请求 1 建立前缀，请求 2 预热缓存传输和 Gather JIT，均不计入统计。
- 请求 3～8 为六个正式请求。所有请求共用前缀，每个请求的第一个后缀 token 不同，防止完整请求重复命中。
- 正式测量过程中不清缓存。每个请求必须有完整结束标记、正确输入/输出长度、纯 GPU 命中；host/storage 命中会中止测试并保存失败原因。
- GPU 命中允许比目标前缀少至多 512 token，以容纳缓存边界对齐；A/B 对应请求的实际命中量仍必须完全相同。

可以覆盖的参数：

```bash
MODE=A BASE=http://10.51.1.3:8848 \
PREFIX_K=512 SUFFIX_K=16 REQUESTS=6 OUTPUT_TOKENS=8 \
MODEL_PATH=/model/Kimi-K3 PREFILL_LOG=log/prefill-A-latest.log \
RESULT_DIR=ab-results/gpu-prefix-run2 PYTHON=python3 \
bash test_scripts/bench.sh
```

两组必须使用相同 workload 参数。每轮用新的 `RESULT_DIR`；已有同模式结果时脚本拒绝覆盖。使用较短前缀可能不触发 A 的回退，此时本测试会明确报错，因为它专门验证长前缀回退场景。

## 3. 结果怎么看

第二组完成后自动打印每个请求的 A/B TTFT、中位数降幅、加速比、B 更快的请求数。正降幅代表改善，负值代表退化。六个样本仅用于快速判断趋势，不作为 P95/P99 结论。

结果目录包含：

- `A-gpu-prefix.json`、`B-gpu-prefix.json`：完整 JSON，各自包含 `valid`、`workload`、`summary`、`samples`、`log_evidence`。与旧 `bench_serving` 的 JSONL 格式不同。
- `A-gpu-prefix.prefill.log`、`B-gpu-prefix.prefill.log`：测量期间的 Prefill 日志副本，保留证据，避免服务重启覆盖日志。
- `comparison.json`：两组通过工作量、样本数和缓存命中检查后才产生的对比。

优先关注：

| 字段 | 用途 |
|---|---|
| `valid` / `error` | 本轮是否有效、无效原因 |
| `summary.median_ttft_ms` | 首 token 延迟的中位数，主要收益指标 |
| `samples[].ttft_ms` | 每个请求的首 token 延迟，单位毫秒 |
| `summary.median_e2e_latency_ms` | 完整请求耗时的中位数 |
| `samples[].meta.cached_tokens_details` | `device` 接近 512K，`host=0`，storage 无命中 |
| `comparison.json` 的 `ttft_reduction_pct` | `(A中位数-B中位数)/A中位数×100%` |
| `comparison.json` 的 `speedup` | A/B TTFT 中位数之比 |

比较时重新验证样本，不仅检查 `valid` 标志。输入 token hash、输出长度、实际缓存命中量不一致时拒绝报告收益。输出文本相同数仅作简单冒烟检查，不能代替准确率测试。

手动重新打印对比：

```bash
python3 test_scripts/bench_gpu_prefix.py compare \
  ab-results/gpu-prefix-run1/A-gpu-prefix.json \
  ab-results/gpu-prefix-run1/B-gpu-prefix.json
```

## 4. 路径日志与 overlap

```bash
rg 'DCP window|falling back to per-token RDMA' "log/prefill-${MODE}-latest.log"
```

- A：`falling back to per-token RDMA` 确认长前缀走了旧路径回退。
- B：`actual=2 x 128 MiB ... window_tokens=...` 确认实际容量；OOM 后可能是 64/32 MiB。
- B：默认每个 chunk 仅打印 `DCP window chunk ... windows=... gathers=... sends=... tokens=... bytes=... ret=0`，汇总该 chunk 的成功窗口，bench 用它校验执行路径。
- 设置 `SGLANG_MOONCAKE_DCP_LOG_DETAILS=1` 并重启 Prefill 后，额外打印逐窗口 `gather_ms`、逐目标 `send_ms`、窗口 `elapsed_ms` 和 `PD_TRANSFER`。正式测 TTFT 建议关闭，两组保持一致。
- 新版 `gather_ms` 从 producer 依赖之后的 CUDA event 开始，不含此前页表上传；包含 Gather 等待执行及执行的时间，不能当作纯 kernel 耗时。`elapsed_ms` 包含从原任务入队以来的等待，不能跨窗口相加。

日志证明路径执行，不证明 Gather/RDMA overlap。下面单独用 nsys 分别采集 A/B 的一个正式请求；性能收益仍使用第 2 节不带 profiler 的结果。

### 4.1 采集 A：关闭窗口化

先结束上一轮自己启动的 Prefill/Decode 服务，释放 GPU 和端口。`prefill.sh` / `decode.sh` 使用 `nohup` 后台启动，退出 `tail -f` 不会停止服务。以下地址沿用第 1 节示例，按实际部署修改。

Decode 节点启动 A（Decode 不需要 nsys）：

```bash
MODE=A SGLANG_MOONCAKE_DCP_WINDOW_PACK=0 \
DECODE_HOST=10.51.1.5 DECODE_PORT=8001 DECODE_BOOTSTRAP_PORT=8998 \
bash test_scripts/decode.sh
```

Prefill 节点终端 1，用 nsys 包住整个启动脚本，采集其子进程中的 CUDA/NVTX 活动：

```bash
mkdir -p nsys-results/gpu-prefix-run1
MODE=A SGLANG_MOONCAKE_DCP_WINDOW_PACK=0 \
SGLANG_MOONCAKE_DCP_PACK_BUFFER_MB=128 \
SGLANG_MOONCAKE_DCP_NVTX=1 \
SGLANG_DISAGG_PREFILL_EARLY_SEND_CACHED_PREFIX=1 \
PREFILL_HOST=10.51.1.3 PREFILL_PORT=8000 PREFILL_BOOTSTRAP_PORT=8998 \
nsys profile --trace=cuda,nvtx,osrt --sample=none --cpuctxsw=none \
  --capture-range=cudaProfilerApi --capture-range-end=stop-shutdown \
  --kill=none \
  --output=nsys-results/gpu-prefix-run1/prefill-A \
  bash test_scripts/prefill.sh
```

等待两端服务和 Router 就绪，在 Prefill 节点终端 2 触发测量：

```bash
MODE=A BASE=http://10.51.1.3:8848 \
PREFIX_K=512 SUFFIX_K=16 REQUESTS=1 OUTPUT_TOKENS=8 \
PROFILE_PREFILL_URL=http://10.51.1.3:8000 \
PREFILL_LOG=log/prefill-A-latest.log \
RESULT_DIR=ab-results/gpu-prefix-profile-run1 \
bash test_scripts/bench.sh
```

`BASE` 是 Router，`PROFILE_PREFILL_URL` 必须直连 Prefill HTTP 端口，不是 bootstrap 端口，也不能填 `0.0.0.0`。benchmark 先清缓存、建立前缀和预热，再调用 `/start_profile`（`activities=["CUDA_PROFILER"]`），正式请求结束后调用 `/stop_profile`。因此 nsys 不采集漫长的模型启动和冷前缀计算。

### 4.3 输出与时间线判读

`/stop_profile` 触发停止采集及报告导出，等待 nsys 提示报告生成完成。预期输出：

```text
nsys-results/gpu-prefix-run1/prefill-A.nsys-rep
nsys-results/gpu-prefix-run1/prefill-B.nsys-rep
ab-results/gpu-prefix-profile-run1/A-gpu-prefix.json
ab-results/gpu-prefix-profile-run1/B-gpu-prefix.json
```

benchmark 还会保存两组测量日志。带 profiling 的结果不参与性能自动对比，不生成收益用的 `comparison.json`。正式测性能时，重新普通启动服务、关闭 NVTX，并在 benchmark 终端 `unset PROFILE_PREFILL_URL`。

把两个 `.nsys-rep` 下载到安装了 Nsight Systems GUI 的机器，分别打开：

- A：长前缀应在服务日志出现 `falling back to per-token RDMA`；旧路径没有这里新增的 `DCP_GATHER` / `DCP_SEND` 标记，不能因缺少这些标记判断未发送。
- B：展开同一个 PP worker 的 CPU 线程 NVTX 和对应 GPU 的 CUDA stream，搜索 `DCP_GATHER` / `DCP_SEND`。标记带有 `pp`、`room`、`buf`、token 范围；同一请求的窗口应交替复用两个缓冲区地址。
- 真正检查 overlap：通过 CUDA launch 关联找到窗口 N+1 的实际 Gather kernel，检查其 GPU 执行区间是否与窗口 N、另一个缓冲区的 `DCP_SEND` CPU 区间相交。NVTX 的 Gather 范围只是 CPU 提交范围，仅两个 CPU 标记相交不够。
- 新增 `DCP_PREPARE`、`DCP_DESCRIPTORS`、`DCP_WAIT_GATHER`、`DCP_SUBMIT_SEND`、`DCP_WAIT_SEND`，区分 CPU 准备、描述符生成、GPU 完成等待和发送等待；NVTX 与详细日志开关相互独立。
- 这证明 Gather 与同步发送调用重叠；发送调用包含排队和完成等待，不能证明网卡在整个区间持续 RDMA。实际网卡流量需结合网卡观测。只有一个窗口，或下一窗口尚未就绪时，不保证出现 overlap。

理想流水如下（示意，不代表实测时间比例）：

```text
时间段       启动              稳态 1              稳态 2            收尾
GPU          Gather N          Gather N+1          Gather N+2
发送线程                       Send N             Send N+1          Send N+2
```

同一窗口必须先 Gather 再发送；要看的是下一窗口 Gather 和上一窗口发送是否在同一时间执行。按 `pp`、`room` 和 `tokens` 找到连续窗口，确认 `buf` 交替，并展开所有相关发送 worker。检查 GPU 上实际 kernel 的区间，不能只比较 CPU 上的 `DCP_GATHER` 范围。Gather 比发送快时，Gather stream 留白是正常的；`DCP_WAIT_SEND` 较长也可能只是下一窗口已准备好、仍在等当前发送完成。若 `DCP_PREPARE` 已结束但实际 Gather 很晚才开始，应继续检查 producer 依赖和主计算竞争。性能改善最终仍以不带 profiler 的 TTFT 为准。

也可先在命令行查看汇总（汇总本身不能证明 overlap）：

```bash
nsys stats --report cuda_gpu_kern_sum,nvtx_sum nsys-results/gpu-prefix-run1/prefill-A.nsys-rep
nsys stats --report cuda_gpu_kern_sum,nvtx_sum nsys-results/gpu-prefix-run1/prefill-B.nsys-rep
```

## 6. 有效传输带宽

有效带宽日志现在按需启用：启动 Prefill 前设置 `SGLANG_MOONCAKE_DCP_LOG_DETAILS=1`。默认关闭逐调用计时和日志以减少开销；开启后两组必须使用相同设置。统计覆盖 `_transfer_data()` 的非空调用（含经过此接口的 KV/state 等），不含绕过此接口的传输，也不等同于网卡线速。关闭时 bench 仍通过 chunk 汇总校验路径，带宽显示缺失。

每次调用打印：

```text
PD_TRANSFER pid=... pp=... peer=... bytes=... descriptors=... start_ns=... end_ns=... send_ms=... effective_GBps=... ret=0
```

`effective_GBps = bytes / (send_ms × 10^6)`，单位是十进制 GB/s。时间从进入同步传输调用前到返回后，包含 Python 参数处理、Mooncake 提交、排队和完成等待；不包含此前 Gather 或线程池排队。日志写入发生在计时结束后，但日志本身仍会给整体测试增加少量开销。失败传输不计成功字节。

`A/B-gpu-prefix.json` 的 `log_evidence.transfer_metrics` 和 `comparison.json` 的 `transfer_metrics.A/B` 保存：

| 字段 | 含义 |
|---|---|
| `successful_bytes` / `descriptors` | 成功调用的总有效字节数／描述符数 |
| `successful_calls` / `failed_calls` | 成功／失败调用次数 |
| `call_send_ms_median` / `call_send_ms_max` | 单调用耗时中位数／最大值 |
| `call_effective_GBps_median` | 单调用有效带宽的中位数，不是所有网卡总带宽 |
| `active_union_GBps` | 总成功字节数除以成功调用时间区间的并集长度；不重复累加并发时间 |
| `span_GBps` | 总成功字节数除以最早开始至最晚结束的跨度；包含调用间空闲、计算和请求间隙 |

时间戳为同一 Prefill 主机上的 monotonic ns，跨 PP 进程可以比较，不可混合多台机器的日志计算并集。上述带宽都是应用侧观测值，不能用于证明 Gather/RDMA overlap。A/B 字节数不同会提示；没有新日志时显示带宽缺失，不会编造为零。

## 7. Gather kernel 改写的独立验证

这组测试比较旧的逐字节 Gather、按行分块 Gather 和融合页索引计算的 Gather，与前面的窗口化 A/B 开关是两个不同的比较。先在空闲 B300 上测 kernel，再测完整服务 TTFT；不要用 kernel 加速比代替端到端收益。源码中的索引重复不能直接解释为同等次数的 HBM 读取，`2 × payload / time` 也只是逻辑读写带宽，实际 HBM 流量需要硬件计数器。

在远端仓库根目录、已有 SGLang 环境运行；仓库有 venv 时优先使用 uv 环境，否则激活 conda `torch` 环境。确保运行的是当前 checkout：

```bash
export PYTHONPATH="$PWD/python${PYTHONPATH:+:$PYTHONPATH}"
python test_scripts/bench_pd_dcp_gather.py \
  --items 2 3 4 --patterns dcp fragmented --include-prepare \
  --output ab-results/gather-kernel-run1/results.json \
  --dump-ptx ab-results/gather-kernel-run1/ptx
```

脚本默认使用 128 MiB 窗口、每行 576 B、DCP=8、page size=64，按实际窗口对齐计算行数；覆盖连续物理页和打散物理页两种 rank-major Gather。三版本使用相同源数据；前两版接收 token 索引，融合版接收物理页表。先与 PyTorch 逐字节核对，再轮换测量顺序运行三轮。输出 GPU、PyTorch/Triton 版本、实际 kernel 文件路径、每轮耗时、中位数、加速比和索引上传字节数。已有 JSON/PTX 文件拒绝覆盖，重跑换结果目录。

`--include-prepare` 另测 CPU 端索引／目标连续段准备，输出 `cpu_preparation.legacy_us` 和 `paged_us` 中位数。新路径复用已缓存的目标连续页段；此统计不含一次性缓存建立、GPU 上传、线程池调度和 RDMA，也不代表完整请求 TTFT。kernel 计时中的页表和 metadata 已上传，须结合服务端 `DCP_PREPARE` 范围检查完整流水。

本次重构已在本机通过混合 item 宽度、非对齐地址、奇数字节宽度、不满一组的行数、重复索引、空输入、CUDA Graph replay、目标描述符和失败释放等检查；专项测试文件按要求移除。这不代表已经验证 B300 的完整服务。保留的 benchmark 仍会逐字节核对三版本输出，也可用 `--rows 17` 等测试小窗口；小窗口计时更容易受 Python 发起开销影响。

单独采集三层满窗的新旧 kernel（无需启动模型）：

```bash
mkdir -p nsys-results/gather-kernel-run1
nsys profile --trace=cuda,nvtx --sample=none --cpuctxsw=none \
  --capture-range=cudaProfilerApi --capture-range-end=stop-shutdown \
  --kill=none --output=nsys-results/gather-kernel-run1/gather \
  python test_scripts/bench_pd_dcp_gather.py \
    --items 3 --patterns fragmented --profile
```

远端先确认 `nsys profile --help` 支持这些选项。profile 模式在编译和正确性检查后开始采集，三版本各执行十次，分别标记 `DCP_GATHER_BASELINE`、`DCP_GATHER_ROW_TILED`、`DCP_GATHER_PAGED_FUSED`，不输出性能加速比。

典型三层满窗为 77,312 行，融合版每 CTA 处理同一 rank 的 16 行，grid 为 `(3, 604, 8)`，CTA 数为旧版的 1/9。每窗口上传 1,208 个 int32 页号（4,832 B），替代 77,312 个 int64 token 索引（618,496 B）；每层源指针、宽度及宽度前缀和只上传一次。GPU 在 Gather 中计算源地址和窗口相关的 pack 偏移，CPU 按缓存的目标连续页段生成 RDMA 描述符。

行宽一致时编译期特化；满足源地址、行宽、目标地址对齐条件时使用 uint32 位拷贝，其余情况走按行的 byte 路径，不做浮点转换。描述符在 Gather 提交后立即准备，实际发送仍等待 ready event；发送完成前不复用 buffer。注册对象变更、session 失败、请求 abort 仍会检查，失败时保留原来的隔离和 drain 约束。

在 B300 上确认逐字节正确且耗时改善后，固定窗口化开启，用旧／新 kernel 分别重启 Prefill 测量相同服务负载。保留 CUDA launch 到 kernel 开始的等待指标：此次改写减少 kernel 内部工作，不保证消除主计算并发时的启动延迟。
